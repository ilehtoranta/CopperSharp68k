# Internal M68k ABI

CopperSharp uses this convention only for calls between methods emitted in the
same closed-world compilation. Internal symbols are compiler-private and have
no compatibility contract with code generated by an older compiler.

## Floating-point values

Single and double values use canonical IEEE-754 bits in the existing D-register
and stack ABI. Native FPU operations marshal those bits through volatile FP0 and
FP1 scratch registers; FP2-FP7 are not allocated or clobbered. SoftFloat uses
the same raw-bit representation, with singles in one longword and doubles in a
high:low longword pair.

## Arguments

Arguments are classified from left to right. Instance `this` is argument zero.
The data and address register banks are allocated independently:

| Argument kind | Registers | Overflow |
| --- | --- | --- |
| 32-bit scalar or transparent scalar | D0, then D1 | stack |
| managed reference, managed pointer, unmanaged pointer, function pointer, `this` | A0, then A1 | stack |
| 64-bit scalar | D0:D1 when both are free | whole value on stack |
| reference-free aggregate | none | whole value on stack |
| shared generic parameter | none | stack |

A shared generic parameter does not consume a register; a later statically
classified parameter may still use an available register. The high long of a
64-bit register argument is in D0 and the low long is in D1. A reference-free
aggregate likewise consumes no data or address register, so later scalar and
reference arguments may continue using their respective banks.

Only overflow arguments are visible on the callee stack. At method entry,
`(A7)` is the return address, the first overflow argument starts at `4(A7)`,
and later overflow arguments follow in declaration order. Every value uses
four-byte slots. A multiword value stores its high long at the lower address.
The caller removes the overflow block after return. A7 remains at least
word-aligned; four-byte slot sizing does not impose a stronger native stack
alignment requirement.

### Examples

- Instance `receiver.Call(int, object)` uses A0 for `this`, D0 for the scalar,
  and A1 for the reference.
- `Call(int, object, int, object, int, object)` uses D0, A0, D1, A1,
  `4(A7)`, and `8(A7)` respectively.
- `Call(void*, int, object, int, byte*)` uses A0, D0, A1, D1, then `4(A7)`.
- `Call(long)` uses D0:D1. In `Call(int, long)`, the `int` uses D0 and the
  entire `long` overflows with its high long at `4(A7)` and low long at
  `8(A7)`.
- `Call<T>(T, int, object)` keeps `T` at `4(A7)` while the later known scalar
  and reference still use D0 and A0.
- `Call(int, Pair, int)` uses D0 for the first scalar, places every `Pair`
  payload word on the stack in layout order, and uses D1 for the final scalar.
- `Call(Pair, Pair)` places both complete values on the stack in declaration
  order; each value's first field is at its lowest argument address.

Register arguments never have shadow stack slots. Unsupported aggregates and
reference-bearing value types remain outside this milestone. For a supported
reference-free aggregate, the caller expands a direct local, argument, or stable
address-backed computed value into stack words in reverse push order, producing
layout order at the callee.
The callee copies the incoming value into a stable full-size frame home before
its body executes. The compiler-private source address used during expansion is
not part of the ABI and never crosses the call.

Computed `unbox.any` and managed-call result values are copied into uninitialized
private frame homes. Their machine-IR values are addresses of those homes, not
addresses of boxed payloads, so collection and calls cannot invalidate them.

A direct managed method returning a reference-free multiword aggregate receives
a compiler-private hidden return-buffer pointer on the stack. It follows all
declared stack arguments and does not consume a data or address register lane.
The caller pushes this pointer before expanding declared stack arguments, the
callee copies every result word into it, and the caller rematerializes the home
address after cleanup. Imported and interface-return adapters remain explicit
future ABI work.

## Results and register preservation

| Result kind | Location |
| --- | --- |
| 32-bit scalar | D0 |
| reference or pointer | A0 |
| 64-bit scalar | high D0, low D1 |
| reference-free multiword aggregate | caller-provided hidden stack buffer |
| void | none |

D0, D1, A0, and A1 are volatile. D2-D7 and A2-A6 are callee-saved; generated
methods save only registers they can write. A7 is the stack pointer. No address
register is reserved as a frame pointer; A5 is allocatable and is restored by
normal epilogues or table-driven exception unwind thunks when a method uses it.

Direct calls, constructors, class virtual calls, interface calls, entry
adapters, export adapters, and linked managed-runtime methods all use this
convention. Tail calls are emitted only when the outgoing layout can be
installed without violating frame restoration; other tail positions use a
normal call and return.

## Managed roots

Register-resident managed references are homed before a GC safepoint. Each
safepoint's exact return PC selects a root map containing signed offsets from
the canonical A7 frame base. Managed-reference overflow slots are recorded
directly; managed pointers are address-class arguments but are not object roots
by themselves.

## External boundaries

This ABI does not change `[M68kImport]`, `[M68kExport]`, or target-platform
library conventions. Their adapters marshal between explicitly declared
physical registers and this internal layout.

Compiler runtime hooks are also explicit boundaries:

| Hook | Contract |
| --- | --- |
| `__c68k_alloc` | size in D0; raw allocated address in D0 |
| `__c68k_dispose` | reference-slot address in A0 |
| `__c68k_gc_init` | config address in D0; nonzero status in D0 |
| `__c68k_gc_collect` | suspended return-address slot in D0; resume PC in D1; method table in A0; static-root table in A1 |
| `__c68k_gc_get_stale_bytes` / `blocks` | result in D0 |
| `__c68k_unhandled_exception` | exception in A0; reason in D0 |

These hook contracts are stable integration surfaces and need not follow the
managed reference-result rule. Unless a hook documents an additional clobber,
it may modify D0, D1, A0, and A1 and must preserve D2-D7 and A2-A6.
